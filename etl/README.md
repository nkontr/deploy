# ETL — загрузка данных «Радара присутствия»

etl-service — отдельный HTTP-микросервис (Python, стандартная библиотека, порт 8084). `python -m etl serve` (CMD контейнера)
поднимает API; загрузка превращает сырьё `etl.raw_*` в `core.*` одной транзакцией. Из консоли по-прежнему работают
`python -m etl load` и `python -m etl demo-project`. Конфиг из env: `DATABASE_URL`, `PORT` (8084), `INTERNAL_TOKEN`,
`AUTO_LOAD` (`if-empty` — по умолчанию: загрузить при старте, если ещё не было успешной; `always`; `never`).
Подключение к БД с повторами (30 × 2 с).

## API

| Запрос | Что делает |
| --- | --- |
| `GET /health` | без токена: `{"status":"ok","running":false}` |
| `POST /internal/etl/load` | запустить загрузку: 202; 409, если уже идёт |
| `GET /internal/etl/status` | `{"running":…, "last":{id, status, startedAt, finishedAt, details}}` |
| `POST /internal/etl/demo-project` | 201 `{projectId, municipality}` — демо для notifier |
| `POST /internal/etl/prices` | парсинг цен калькулятора: 202; 409, если уже идёт |
| `GET /internal/etl/prices/status` | `{"running":…, "last":{status, startedAt, finishedAt, details}}` из `etl.price_run` |

`/internal/*` — заголовок `X-Internal-Token`. Ошибки — в общем формате `{"error":{"code","message"}}`. Во время загрузки
читатели `core.*` ждут конца транзакции (TRUNCATE держит блокировку) — перезапускать на демо не стоит.

## Блок для docker-compose.yml (PR техлиду)

```yaml
  etl:
    build: ./etl
    container_name: radar-etl
    environment:
      PORT: "8084"
      DATABASE_URL: postgresql://etl_loader:${ETL_DB_PASSWORD:-etl_dev}@postgres:5432/radar
      INTERNAL_TOKEN: ${INTERNAL_TOKEN:-internal_dev_token}
      AUTO_LOAD: if-empty
    depends_on:
      postgres:
        condition: service_healthy
    restart: unless-stopped
```

Сервис больше не «разовый»: готовность — `etl.load_run.status = 'ok'` (`GET /internal/etl/status`), а не код выхода 0.
Это меняет `infra/smoke.sh` и критерий готовности из ТЗ — согласовать с техлидом. Наружу (nginx) путь не открывать.

## Координаты компании

В реестре МСП адреса нет — только район, город и населённый пункт.

1. **Юрлица с адресом из ЕГРЮЛ** (`etl/addresses.py`, DaData «Организация по ИНН», кэш `etl.egrul_address`):
   точка на юридическом адресе, если DaData дала координаты дома (`qc_geo` 0/1) в пределах области →
   `geo_precision = 'address'`, адрес — в `core.company.address` и в карточке. У ИП адрес в ЕГРИП закрыт.
2. **Остальные** — в **центре населённого пункта** (`settlements.json`; центр проверяется застройкой района из
   `buildings.csv.gz` — одноимённый хутор в чужом районе отбрасывается) → `'settlement'`, иначе в центре района /
   городского округа → `'municipality'` (`etl/geo.py`). Не на случайном здании: точка на доме выглядела бы как
   адрес, а кластеры по таким точкам выдумывали бы, где внутри города компаний больше.

На карте: обзор и тепло — по этим точкам; на масштабе улиц (`MapController.STREET_ZOOM`) точками — только
компании с адресом, остальные — одним значком на населённый пункт. Без `DADATA_API_KEY` адресов нет ни у кого.
Адреса: запрос раз в сутки сам (лимит `DADATA_DAILY_LIMIT`, 9 000 из бесплатных 10 000), вручную —
`POST /internal/etl/addresses` или `python -m etl addresses`; очередь — клиенты РТ, потом по выручке.
Счётчики — `etl.load_run.details.geo_precision`.

Пересобрать данные (нужен интернет, ~1 ч):

```bash
python etl/tools/geocode_nominatim.py --rmsp etl/data/rmsp_61.csv.gz --case infra/db/tools/case.xlsx \
    --user-agent "radar-hackathon (you@example.com)" --settlements
python etl/tools/fetch_osm_buildings.py --user-agent "radar-hackathon (you@example.com)"
```

## Парсинг цен калькулятора

Кейс (слайд 3): «оценка стоимости проекта … и парсингом цен на оборудование/ПО». `etl/prices.py`, итог — `etl.price_run`:

1. **Прайс-листы Ростелекома для юрлиц** (PDF с rostov.rt.ru/b2b: видеонаблюдение, виртуальная АТС, Wi-Fi) →
   `calc.component.base_price`, `price_source`, `price_date` («Тарифы действуют с …»; у Wi-Fi — дата PDF).
   Модели камер, которых нет в каталоге, добавляются. Сайт недоступен — разбираются копии `data/prices/*.pdf`.
2. **tinko.ru** — рыночная цена аналога той же серии (у Ростелекома названия короткие или устаревшие, в магазине —
   новые ревизии): минимум и медиана по видеокамерам серии → `market_*`. Не ответил — прежние значения остаются.

Позиции МОД3 из таблицы кейса не трогаются. Запуск: после старта, если за `PRICES_EVERY_HOURS` (24) удачного не было,
дальше по таймеру; вручную — `POST /internal/etl/prices` (в калькуляторе — кнопка «Обновить цены» для admin)
или `python -m etl prices`. Тесты на сохранённых PDF и выдаче tinko: `python -m pytest etl/tests`.

## Записи «Не является субъектом МСП»

В выгрузке реестра у ~56 % строк категория «Не является субъектом МСП» (статуса МСП уже нет). По умолчанию
(`NON_MSP=exclude`) такие не-клиенты не загружаются (это не рынок МСП), а клиенты из этой категории получают
`status='excluded'`. `NON_MSP=keep` возвращает прежнее поведение (все считаются действующими).
Счётчики — в `etl.load_run.details.skipped` (`non_msp_not_loaded`, `clients_non_msp_marked_excluded`).

## Статус компании

| ИНН есть в… | `is_client` | `status` | `excluded_at` |
| --- | --- | --- | --- |
| клиентах и действующем реестре | true | active | — |
| клиентах и выгрузке исключённых | true | excluded | дата из выгрузки |
| клиентах, нигде в реестре | true | excluded | — |
| только в действующем реестре | false | active | — |
| только в выгрузке исключённых | не загружается | | |

## Формулы

- **Муниципалитет:** район, иначе город → нижний регистр → `г. Название` / `Название р-н` → заглавные буквы (кроме `на`, `в`).
- **Координаты:** точка в круге вокруг центроида (радиус 0,01° населённый пункт / 0,03° город / 0,08° район):
  `r = R·√u(inn,"r")`, `φ = 2π·u(inn,"phi")`, `lat = lat0 + r·cosφ`, `lon = lon0 + r·sinφ / cos(lat0)`.
  `u(inn, salt) = int(sha256(inn+salt)[:8], 16) / 0xFFFFFFFF` — стабильно между запусками.
- **Выручка:** юрлица из ФНС — доход за последний год (`revenue_source='fns'`); данные — `tools/fns/prepare_revenue.py`
  (открытые данные ФНС за 2024 и 2025 год). Остальным — модель: `медиана × k_отрасли × exp(0.6·(u−0.5)·2)`, медиана:
  micro ИП 4 млн / ЮЛ 15 млн, small 250 млн, medium 1,2 млрд (или `employees × 3 млн`), результат обрезается границами
  категории (micro ≤ 120 млн, small 120–800 млн, medium 0,8–2 млрд; нижняя граница micro 0,5 млн — наше допущение).
  `revenue_source='model'`, `is_estimated=true`.
- **Рост (ФНС):** год к году, только если доход **в обоих годах ≥ 1 млн ₽**, и в пределах **−90…+300 %**: на маленькой
  базе выходят тысячи процентов, а реальные скачки (запуск, реорганизация) забивают сортировку «по росту». Иначе
  (один год в ФНС, база меньше 1 млн) — рост по модели ниже. На данных: реальный рост у ~23 тыс. юрлиц, медиана +0,5 %.
- **Рост (модель)** — **откалиброван по реальному росту ФНС** (`tools/calibrate_growth.py`, ~22 тыс. юрлиц области):
  точка между квартилями роста своей отрасли (p25…p75, медиана в центре) по хэшу ИНН + **9 п. п.** компаниям, которые
  в реестре МСП не дольше 5 лет (медиана молодых +8,8 % против −0,7 % у остальных). Примеры медиан: агро −24 %,
  торговля и логистика −6 %, производство −1 %, недвижимость +7 %, ИТ и услуги +11 %. Модель не выдумывает крайних
  значений — все оценки внутри межквартильного диапазона отрасли. Ограничения: калибровка по юрлицам (у ИП отчётности
  в ФНС нет); возраст — по дате включения в реестр МСП (у всех, кто старше реестра, это 01.08.2016).
- **Потенциал и белые пятна:** `core.refresh_municipality_stats()` в БД (`infra/db/init/02_tables.sql`) — единая формула
  для ETL и core-api; пороги калибруются на реальных данных.
- **Инвестпроекты (продукт 2):** стадия — `start_year ≥ текущий год` → design, `launch_year ≤ текущий год` → launch,
  иначе construction (год — `model.CURRENT_YEAR`). **Допущение:** лист МОД2 — реестр планов, и проект со стартом в
  текущем году ещё на этапе проекта и разрешений (стартов позже 2026 в данных нет, при строгом «>» проектирование
  было бы пустым). Сейчас: проектирование 8, строительство 34, запуск 21;
  отрасль и потребности — по ключевым словам (`data/invest_keywords.csv`, первое совпадение, слово ищется с начала
  слова), ручные правки — `data/invest_overrides.csv`. **Порядок строк важен:** стройка → агро → энергетика →
  недвижимость → производство → логистика → торговля → гостиницы/общепит → услуги — так «ЖК … Летний сад» не уходит в
  агро, а «расширение производства… строительство склада» — в логистику. Сейчас все 63 проекта получают отрасль и
  потребности; в overrides — 3 проекта, которые словами не разобрать (медцентр по названию бренда, СТО при складе,
  бывший комбикормовый цех под ремонт техники).

## Порядок первого запуска

1. Выгрузить реестр и прогнать `tools/rmsp/prepare_rmsp.py` (см. `docs/data/rmsp-instruction.md`).
2. `python etl/tools/geocode_nominatim.py --rmsp etl/data/rmsp_61.csv.gz --case infra/db/tools/case.xlsx --user-agent "..."`
   (+ `--settlements` по желанию) → закоммитить JSON.
3. `docker compose up -d --build` → контейнер `etl` завершается с кодом 0, итоговые цифры — в логе и в `etl.load_run`.
